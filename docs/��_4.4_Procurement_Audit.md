## 1. EXECUTIVE SUMMARY

### Ответы на 4 ключевых вопроса:

**1. Что Supply считает потребностью?**
> Need = SUM(recipe_item.consumption_kg) для рецептов со статусом `active`.

**2. Что Supply считает доступным количеством сейчас?**
> available_now = plant_qty + lip_qty (после ТЗ 4.3). Inbound НЕ включается.

**3. Как Supply определяет дефицит?**
> deficit = need - available_now. Если < 0 → дефицит.

**4. Как Supply определяет количество к закупке?**
> cover_by_purchase = MAX(0, need - on_hand). Единой формулы qty后勤 нет — расчёт ведётся по статусам (ok/control/buy/urgent).

### Статусы:

```
Lead Time    = NOT IMPLEMENTED (поле существует, не используется)
Safety Stock = IMPLEMENTED (min_stock_kg в sku, используется в Planning)
MOQ          = NOT IMPLEMENTED
```

## 2. PROCUREMENT PIPELINE

```
Recipe (active)
    ↓ SUM(consumption_kg)
Recipe Item
    ↓ GROUP BY SKU
Need (pgGetNeedTotals)
    ↓
Stock (getLatestPlantStock + getLatestLipStock)
    ↓ available_now = plant + lip
    ↓ consumed = Need
    ↓
Deficit = need - available_now
    ↓
Dashboard decisions: cover_by_purchase = MAX(0, need - on_hand)
    ↓
Planning status: ok / control / buy / urgent
```

**Ключевой факт:** PurchaseQty (сколько именно купить) **НЕ РАССЧИТЫВАЕТСЯ**. Система только определяет **статус** (ok/control/buy/urgent) и **дефицит**. Конкретное количество к закупке определяется закупщиком вручную.

## 3. ФОРМУЛЫ

### 3.1 Available Now (после ТЗ 4.3)

```
available_now = plant_qty + lip_qty
```

**Файл:** `postgresSupplyService.ts:349`

### 3.2 Consumption

```
consumed[sku] = SUM(recipe_item.consumption_kg)
                WHERE recipe.status = 'active'
                GROUP BY sku
```

**Файл:** `postgresSupplyService.ts:334` (getRecipeConsumption)

### 3.3 Deficit (Live Stock)

```
deficit = available_now - consumed
  = (plant + lip) - consumed
```

**Файл:** `postgresSupplyService.ts:349`

### 3.4 Planning Qty Today

```
qty_today = plant_qty + lip_qty (без inbound — TZ 4.3)
```

**Файл:** `planningStatus.ts:96`

### 3.5 Planning Status

```
need_ratio = qty_today / avg_monthly_usage
final = need_ratio / coefficient

if final > 1.5  → "ok"
if final > 1.0  → "control"
if final >= 0.6 → "buy"
else             → "urgent"
```

**Файл:** `planningStatus.ts:74-84`

### 3.6 Dashboard Decisions

```
on_hand = plant_qty + lip_qty + inbound_qty
need = planned_need

polotsk_side = plant_qty + inbound_qty
polotsk_deficit = MAX(0, need - polotsk_side)
cover_by_transfer = MIN(lip_qty, polotsk_deficit)
cover_by_purchase = MAX(0, need - on_hand)
```

**Файл:** `dashboard.ts:242-254`

**ВНИМАНИЕ:** Dashboard ещё включает inbound_qty в on_hand — это legacy поведение. После ТЗ 4.3 on_hand должен быть plant+lip для决策. Дашборд использует `computePlanningRows()` для светофора (qty_today = plant+lip), но `computeDecisions()` для таблицы решений (on_hand = plant+lip+inbound).

### 3.7 Stock Signal

```
available = plant + lip - consumed

if available < 0       → "critical"
if plant - consumed < 0 → "transfer"  (plant不足, нужен перенос с Lip)
else                    → "ok"
```

**Файл:** `postgresSupplyService.ts:317-322`

### 3.8 SKU Fields (potential thresholds)

```
min_stock_kg: DOUBLE PRECISION  — есть данные (5 SKU)
reorder_point_kg: DOUBLE PRECISION — есть данные (5 SKU)
shelf_life_days: INTEGER — есть данные (некоторые SKU)
```

**Файл:** `schema.ts:113-115`

**Использование:** `min_stock_kg` и `reorder_point_kg` **фактически не используются** в текущих расчётах. Они есть в schema, есть данные, но ни planningStatus, ни dashboard, ни liveStock их не читают.

## 5. NEED

| Аспект | Факт |
|--------|------|
| Создание | Автоматически при INSERT/UPDATE recipe_item |
| Единицы | кг (consumption_kg) |
| Привязка к рецепту | Да (recipe_id FK) |
| Привязка к периоду | Да (period, YYYY-MM) |
| Учитывает остатки | НЕТ — Need = расход, не дефицит |
| Учитывает Inbound | НЕТ |
| Один SKU — несколько Need | ДА (от разных рецептов) |
| Need = Purchase? | НЕТ — Need ≠ Purchase Qty |

## 6. STOCK (AFTER ТЗ 4.3)

```
available_now = plant_qty + lip_qty
```

### Где используется:

| Функция | Формула | Inbound? |
|---------|---------|:--------:|
| getLiveStock | available = plant + lip - consumed | ❌ НЕТ |
| planningStatus | qty_today = plant + lip | ❌ НЕТ |
| Dashboard decisions | on_hand = plant + lip + inbound | ⚠️ ДА (legacy!) |
| stockSignal | stockSignal(plant, lip, consumed) | ❌ НЕТ |

### Legacy / непоследовательность

Dashboard `computeDecisions()` ещё использует `on_hand = plant + lip + inbound_qty`. Это **противоречит ТЗ 4.3**, но не исправлено, поскольку TZ 3.5.1 не требовал менять Dashboard decisions.

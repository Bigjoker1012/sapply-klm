СТОП. Больше ничего не исправляй точечно.

После последних изменений появилась новая критическая ошибка.

На странице «Рецепты» все 223 рецепта имеют фактический статус archived, но интерфейс показывает:

Активные — 0
В работе — 223
Отменённые — 0
Все — 223

При этом в каждой строке отображается status = archived.

Это означает, что фактический статус рецепта и категория фильтрации UI расходятся.

Задача

Проведи аудит всей логики статусов рецептов до внесения каких-либо исправлений.

Проверь последовательно:

Какие значения status реально хранятся в PostgreSQL.
Какие значения возвращает API /api/recipes.
Как backend преобразует status в категорию:
active
in_work
archived
cancelled
Как frontend распределяет полученные рецепты по вкладкам:
«Активные»
«В работе»
«Отменённые»
«Все»
Найди функцию/маппинг, из-за которого archived попадает в В работе.
Отдельно проверь операции:
отменить активный рецепт;
отправить в архив;
вернуть из архива;
разбить рецепт.
Для каждой операции проверить полный путь:

кнопка → frontend → API → backend → PostgreSQL → ответ API → обновление списка

ВАЖНО

Не считать проблему исправленной только потому, что в строке отображается archived.

Должны одновременно выполняться условия:

Архивный рецепт:

находится только во вкладке «Архив» / соответствующей архивной категории;
не находится в «Активные»;
не находится в «В работе»;
не может быть отменён как активный;
может быть разбит, если это предусмотрено бизнес-логикой.

Активный рецепт:

находится в «Активные»;
сотрудники могут его отменить;
может быть разбит.

Отменённый рецепт:

находится только в «Отменённые».
Особенно важно

Не менять названия статусов, не делать новый формат статусов и не переписывать существующие данные.

Сначала дай мне:

1. фактические значения status в БД;
2. текущий mapping status → category;
3. где именно возникает ошибка;
4. какие строки кода отвечают за фильтрацию;
5. почему у меня и сотрудников различается возможность выполнения операций.

Только после этого предложи исправление.

И ещё один момент

На твоём скрине я вижу «Разбить» даже у архивного рецепта. Это тоже неправильно, если по нашей логике разбивать можно только рецепт, который действительно допускает эту операцию.

Поэтому я бы не разрешала Кексу сейчас ещё что-либо коммитить. Пусть сначала проведёт этот аудит и покажет нам карту:

статус в БД → API → категория → кнопки → endpoint → результат.

Потому что сейчас у нас уже не одна ошибка. У нас, похоже, рассинхронизация модели статусов между backend и frontend.

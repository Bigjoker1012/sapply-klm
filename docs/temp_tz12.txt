ТЗ 1.2 — Разделение объёма и отмена рецепта

После исправления фильтрации статусов и дат выявлены две новые проблемы.

1. НЕ РАБОТАЕТ «Разбить» — ни у администратора, ни у сотрудников

На странице «Склад и рецепты» кнопка/действие «Разбить» не позволяет разделить объём рецепта.

Требуется

Проверить полный путь:

Frontend
→ обработчик «Разбить»
→ API endpoint
→ backend
→ БД

Нужно установить конкретную причину отказа.

Проверить:
Какой endpoint вызывается при нажатии «Разбить».
HTTP method.
Request body.
Response status.
Response body.
Ошибки в backend log.
Проверку статуса рецепта.
Проверку прав пользователя.
Корректность recipe_id / uid.
Возможность разделения объёма для рецепта со статусом active.
Важно

Не считать проблему решённой, если кнопка просто стала нажиматься.

После разделения должно происходить фактическое изменение данных.

Пример:

Исходный рецепт:
100 т

Разбить:
40 т + 60 т

Результат:
исходный рецепт → 40 т
новый рецепт → 60 т

Конкретную бизнес-логику разделения взять из существующей реализации проекта, не придумывать новую.

Обязательный тест

Проверить разделение под учётной записью администратора.

Если не работает — определить причину и исправить.

Затем проверить под учётной записью сотрудника.

2. СОТРУДНИКИ НЕ МОГУТ ОТМЕНИТЬ АКТИВНЫЙ РЕЦЕПТ

Проблема сохраняется после предыдущего исправления.

Администратор и сотрудники должны иметь разные права только там, где это предусмотрено системой.

Требуется установить:
Какой endpoint вызывается при выборе:
Статус → Отменить
Какой ответ получает сотрудник:
401?
403?
404?
500?
другой?
Что получает администратор при том же действии.
Проверить middleware авторизации и проверки роли.
Проверить backend-функцию изменения статуса.
Проверить допустимость перехода:
active → cancelled
Проверить, не используется ли где-нибудь старое название роли/права.
Проверить, не маскируется ли ошибка авторизации под 404.
Критически важно

Не давать сотруднику право отмены просто удалением проверки на frontend.

Право должно корректно проверяться на backend.

3. Проверить предыдущую ошибку /status

Ранее в DevTools была обнаружена:

GET /api/recipes/{recipe}/status
→ 404 Not Found

Обязательно проверить, связана ли эта ошибка с двумя текущими проблемами.

4. Сравнительный тест

Провести одинаковые действия:

Действие	Администратор	Сотрудник
Разбить active-рецепт	проверить	проверить
Отменить active-рецепт	проверить	проверить
Перевести в архив	проверить	проверить
Посмотреть статус	проверить	проверить

Для каждого неработающего действия предоставить:

Endpoint:
Method:
Request:
HTTP status:
Response:
Причина:
Исправление:
Критерий готовности

Считать ТЗ выполненным только после реального теста через интерфейс:

Разбить
active рецепт
↓
Разбить
↓
введён объём
↓
созданы/изменены необходимые записи
↓
объёмы корректны
↓
статусы корректны
Отменить
active рецепт
↓
Сотрудник → Отменить
↓
операция разрешена согласно его правам
↓
status = cancelled
↓
рецепт исчезает из «Активные»
↓
появляется в «Отменённые»
↓
счётчики обновляются

Не менять структуру БД и бизнес-логику без необходимости. Сначала найти фактическую причину отказа.

И я бы добавила Кексу отдельную фразу, Андрюха:

«Не пиши мне “исправлено”, пока сам через браузер не выполнишь оба действия и не покажешь результат API и состояние страницы после операции».

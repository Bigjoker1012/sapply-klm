ТЗ 1.1 — Исправить фильтрацию и управление статусами рецептов

Обнаружена критическая несогласованность страницы «Склад и рецепты».

На вкладке «Активные» отображаются рецепты, у которых фактический статус archived.

Пример: страница показывает:

Активные: 222
В архив: 0
Отменённые: 0

При этом строки имеют:
Статус = archived

Требуется:
Найти источник формирования:
количества «Активные»;
количества «В архив»;
количества «Отменённые»;
списка рецептов для каждого фильтра.
Проверить, используется ли для фильтрации фактическое поле статуса из БД, а не устаревшее/расчётное поле.
Для фильтра «Активные» должны попадать только рецепты с допустимым активным статусом.
Для фильтра «В архив» должны попадать только рецепты:
status = archived.
Для фильтра «Отменённые» — только:
status = cancelled / фактическое значение, используемое проектом.
Счётчики сверху должны рассчитываться из тех же данных/статусов, что и сами списки.
Нельзя допустить ситуацию:
Активные 222, но в списке строки имеют status = archived.

Проверить действия:

«В план»
«В архив»
«Отменить»
«Разбить»

Для архивного рецепта «Разбить» должно быть запрещено — это нормально.
Но архивный рецепт вообще не должен находиться во вкладке «Активные».

Проверить endpoint:
/api/recipes/{recipe}/status

и предыдущую ошибку 404, обнаруженную в DevTools.

Отдельно проверить права сотрудников: поведение администратора и обычного сотрудника должно быть одинаковым в части доступных действий, если права на операцию одинаковые.
Обязательные тесты после исправления

Создать/найти минимум по одному рецепту каждого статуса:

Статус	Активные	Архив	Отменённые	Разбить
active	✅	❌	❌	✅
archived	❌	✅	❌	❌
cancelled	❌	❌	✅	❌

Проверить также правильность счётчиков.

Важно: не исправлять проблему простым скрытием archived на frontend. Необходимо найти и исправить источник неправильной выборки/фильтрации.

И ещё один момент, который меня настораживает

На скриншоте один рецепт имеет дату:

46210

вместо нормальной даты 10.09.2026.

Это уже второй признак, что при загрузке/преобразовании данных рецептов где-то нарушается типизация или форматирование.

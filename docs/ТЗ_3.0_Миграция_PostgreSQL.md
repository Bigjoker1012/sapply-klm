## 1. ГЛАВНАЯ ЗАДАЧА — ОТВЕТ

> Какие данные сейчас хранятся в Google Sheets, как они используются приложением и как их правильно перенести в серверную БД PostgreSQL?

**Ответ:** Все данные бизнес-логики (остатки, рецепты, потребность, транзит, справочники) хранятся в 13 листах Google Sheets через `sheetsService.ts` (1825 строк). PostgreSQL используется только для авторизации (10 таблиц: user, session, organization, warehouse, sku, supplier, upload_job, upload_row, document_archive, purchase_plan_setting). Остальные 12 таблиц PostgreSQL (batch, stock_movement, recipe, recipe_item, in_transit, transfer, purchase_order и др.) определены в schema.ts, но НЕ используются ни одним роутом.

## 3. МОДЕЛЬ ДАННЫХ КАЖДОГО ЛИСТА

### 3.1 Syryo (Справочник сырья)

- **PK:** raw_uid (текст, формат RAW_xxx)
- **Связи:** ссылается из всех остальных листов по raw_uid
- **Проблема:** нет FK constraints, целостность не гарантирована

### 3.2 Aliases (Синонимы)

- **PK:** id (текст, AL_xxx или raw_uid для старого формата)
- **Два формата строк:** NEW (AL_xxx | raw_uid | synonym | source) и OLD (raw_uid | synonym | type | source)
- **Проблема:** два формата в одном листе, старые коды (RAW030) не совпадают с каталогом (RAW_030)

### 3.3 PlantStock (Остатки Полоцка)

- **PK:** нет (снимок = набор строк по дате)
- **Логика:** каждая загрузка = полный снимок на дату. sumLatestSnapshot берёт max дату.
- **Проблема:** нет уникального ID строки, дубли возможны

### 3.4 LipStock (Остатки Липковской)

- **PK:** нет (аналогично PlantStock)
- **Колонки:** snapshot_date, raw_uid, name, qty_on_hand, reserved_qty, free_qty, unit, source, flag

### 3.5 LipBatches (Партии Липковской)

- **PK:** нет (снимок по дате + raw_uid + batch_code)
- **Колонки:** snapshot_date, raw_uid, batch_code, vendor_name, qty, unit, source, expiry_date, manufacture_date

### 3.6 Inbound (Товары в пути)

- **PK:** id (текст, IN_Date.now())
- **Проблема:** ID генерируется через Date.now() — коллизии при параллельных запросах
- **Статусы:** "в пути", "получено", "удалено" (мягкое удаление)

### 3.7 Need (Потребность)

- **PK:** id (текст, NEED_Date.now())
- **Связи:** recipe_uid → Recipes, raw_uid → Syryo
- **Проблема:** нет FK, deducted (col F) всегда 0 — механизм списания не реализован

### 3.8 Recipes (Рецепты)

- **PK:** recipe_uid (текст, REC_Date.now())
- **Статусы:** "план", "в работе", "архив", "отменён", "удалён"
- **Проблема:** ID через Date.now(), нет версионирования

### 3.9 RecipeLines (Состав рецептов)

- **PK:** id (текст, RL_Date.now_i)
- **Связи:** recipe_uid → Recipes, raw_uid → Syryo
- **Проблема:** deleteRecipe не работал (фильтр по r[0] вместо r[1]) — исправлено в ТЗ 2.5

### 3.10 ReviewQueue (Очередь распознавания)

- **PK:** id (текст, RQ_xxx)
- **Статусы:** resolved TRUE/FALSE

### 3.11 Excluded (Исключённые)

- **PK:** normalized_text
- **Назначение:** позиции, которые не являются сырьём

### 3.12 Analogs (Аналоги)

- **PK:** id (текст, AN_Date.now())
- **Связи:** raw_uid → Syryo, analog_raw_uid → Syryo

### 3.13 AppLog (Лог)

- **PK:** нет (append-only)
- **Колонки:** timestamp, level, message, detail

#### stock_snapshot (Снимки остатков)

```sql
CREATE TABLE stock_snapshot (
  id SERIAL PRIMARY KEY,
  warehouse_id INTEGER NOT NULL REFERENCES warehouse(id),
  snapshot_date DATE NOT NULL,
  source TEXT NOT NULL,                    -- имя файла

CREATE INDEX idx_stock_snapshot_date ON stock_snapshot(warehouse_id, snapshot_date DESC);
```

## 5. СРАВНЕНИЕ GOOGLE SHEETS И POSTGRESQL

| Возможность | Google Sheets сейчас | PostgreSQL |
|------------|---------------------|------------|
| **История** | Снимки по датам в одном листе ( PlantStock, LipStock). Рост строк. | Отдельная таблица snapshots + items. Нормализовано. |
| **Связи** | Нет. Связи поддерживаются кодом (raw_uid в разных листах). | FK constraints. Целостность гарантирована БД. |
| **Уникальность ID** | Нет. Date.now() — коллизии. Нет уникальных constraints. | SERIAL PK + UNIQUE constraints. |
| **Транзакции** | Нет. Clear → write — данные теряются при сбое. | BEGIN/COMMIT/ROLLBACK. ACID. |
| **Одновременная работа** | Rate limit 8 req/sec. Сериализация через мьютекс в коде. | Неограниченно (connection pool). |
| **Контроль целостности** | Нет. Парсер может записать что угодно. | CHECK constraints, NOT NULL, FK. |
| **Производительность** | ~300ms на запрос (HTTP round-trip). Кэш 30 сек. | <1ms (локальный). |
| **Аудит изменений** | Нет (кроме истории версий Sheets). | event_log таблица + триггеры. |
| **Работа локально** | Нет (требует интернет). | Да (локальный PostgreSQL). |
| **Зависимость от интернета** | Да. Сбой Sheets = сбой всего приложения. | Нет. |
| **Резервное копирование** | Google Takeout (ручное). | pg_dump (автоматически, cron). |
| **Объём данных** | ~5000 строк на лист (лимит). | Без ограничений. |
| **Консистентность** | Данные могут разойтись между листами. | FK + транзакции = консистентность. |

## 7. ПЛАН МИГРАЦИИ (ПО ЭТАПАМ)

### Этап 1 — Подготовка (1-2 дня)

1. Создать миграции Drizzle для новых таблиц (stock_snapshot, stock_snapshot_item, raw_material_alias, review_queue, excluded_item, material_analog, need, inbound_shipment)
2. Пересмотреть существующие таблицы recipe, recipe_line, in_transit под реальную структуру
3. Написать seed-скрипт для заполнения sku из Syryo

### Этап 2 — Параллельная запись (3-5 дней)

1. Реализовать dual-write: каждая операция пишет и в Sheets, и в PostgreSQL
2. Сравнить данные после каждого write — расхождений быть не должно
3. Это позволяет откатиться на Sheets в любой момент

### Этап 3 — Переключение чтения (3-5 дней)

1. Переключить read-операции с Sheets на PostgreSQL (по одной таблице)
2. Приоритет: Syryo → PlantStock → LipStock → Recipes → RecipeLines → Need → Inbound
3. После каждого переключения — тестирование Dashboard, Planning, Stock

### Этап 4 — Удаление dual-write (1-2 дня)

1. Убедиться, что все чтения идут из PostgreSQL
2. Удалить запись в Sheets
3. Оставить Sheets только для экспорта (если нужно)

### Этап 5 — Очистка (1 день)

1. Удалить sheetsService.ts (или оставить только экспортную функцию)
2. Удалить database.sql
3. Обновить документацию

## 8. РИСКИ И МИТИГАЦИЯ

| Риск | Митигация |
|------|----------|
| Потеря данных при миграции | Dual-write + бэкап Google Sheets перед миграцией |
| Расхождение данных | Параллельная запись + автоматическое сравнение |
| Даунтайм | Миграция поэтапная, Sheets остаётся как fallback |
| Rate limit Sheets при dual-write | Увеличить MAX_RPS или снизить частоту writes |
| Несовместимость форматов данных | Написать миграционные скрипты с валидацией |

## 10. РЕКОМЕНДАЦИЯ

**Рекомендуется начать с Этапа 1** — создать миграции и seed-скрипт. Это не затронет текущую работу, но подготовит инфраструктуру для миграции.

**Ключевой принцип:** миграция должна быть пошаговой и обратимой. На каждом этапе можно откатиться на Google Sheets без потери данных.

## 4. Date.now() USAGE

### 4.1 recipe.recipe_uid (text business ID)

**Location 1:** `pgWriteRecipe()` — line 394
```typescript
VALUES (${recipe.code + '_' + Date.now()}, ...)
```
**Purpose:** Generate unique recipe_uid when creating new recipe.
**Used as FK:** recipe_item.recipe_id → recipe.id (serial PK), need.recipe_id → recipe.id, document_archive.recipe_uid → recipe.recipe_uid.
**Risk:** LOW — `recipe_uid` is a text field, not PK. Two simultaneous creates would need to happen within the same millisecond. The serial PK (`id`) still ensures uniqueness. However, duplicate `recipe_uid` would violate the implicit business constraint.

## 6. COLLISION RISK ANALYSIS

### recipe.recipe_uid

**Format:** `CODE_TIMESTAMP` (e.g., `Д-П60-3/Б30/ПЛЦ-194_1789025161833`)
**Generation:** `recipe.code + '_' + Date.now()`
**Uniqueness guarantee:** Millisecond timestamp + recipe code
**Collision scenario:** Two recipes with the same code created in the same millisecond
**Mitigation:** `Date.now()` has millisecond precision; recipe creation is manual (human speed)
**Race condition:** `pgWriteRecipe` is called inside `withStockMutation` for most paths, but not all
**Existing duplicates:** 0

### Unique constraint

There is **NO unique constraint** on `recipe.recipe_uid` in PostgreSQL.

The schema defines:
```typescript
recipe_uid: text("recipe_uid"),
```

Without UNIQUE, the database won't prevent duplicates at the DB level. However, the serial PK (`id`) still provides unique row identification.

## 9. RECOMMENDATIONS

| Entity | Current | Risk | Recommendation |
|--------|---------|------|----------------|
| **All tables (PK)** | serial | SAFE | **Option D:** No change needed |
| **recipe.recipe_uid** | Date.now() text | LOW | **Option C:** Keep as business ID, but add UNIQUE constraint |
| **Auth tokens** | Date.now() timestamps | SAFE | **Option D:** No change needed |

### recipe.recipe_uid — Detailed Recommendation

**Option C (recommended):** 
1. Add `UNIQUE` constraint on `recipe.recipe_uid`
2. Keep current `Date.now()` generation (works for manual use)
3. In future, if batch import is needed, switch to `crypto.randomUUID()` for recipe_uid

**Why not Option A (full migration):**
- `recipe_uid` is used as FK in document_archive and referenced in frontend
- Changing format would require data migration + API changes + frontend updates
- Current format works correctly for human-speed recipe creation

**Why not Option B (UUID):**
- Overkill for this use case
- Would break existing references in documents

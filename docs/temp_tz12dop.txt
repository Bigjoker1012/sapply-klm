ТЗ 1.2.1 — ДОКАЗАТЬ причину 404 для сотрудников

Предыдущая проверка «endpoint не имеет ограничений по ролям» недостаточна.

На реальном компьютере сотрудника DevTools показывает:

/api/recipes/{encoded_uid}/status → 404
/api/recipes/{encoded_uid}/tons   → 404

При этом на компьютере администратора отмена активного рецепта работает.

Не считать проблему исправленной по результату анализа кода. Необходимо воспроизвести её непосредственно через браузер сотрудника.

Шаг 1. Сравнить запрос администратора и сотрудника

Для одного и того же рецепта получить из Network:

полный Request URL;
HTTP method;
Status Code;
Response body;
Request Headers;
Cookie/session;
Authorization;
Origin;
Referer.

Сравнить запросы администратора и сотрудника побайтно там, где это возможно.

Шаг 2. Проверить UID

Убедиться, что {uid} у администратора и сотрудника абсолютно одинаковый.

Проверить:

кириллицу;
/;
пробелы;
%D0... URL encoding;
регистр;
дополнительные символы.
Шаг 3. Проверить backend

Для:

GET /api/recipes/:uid/status

и

POST/PUT/PATCH /api/recipes/:uid/tons

установить:

существует ли route;
какое middleware выполняется;
есть ли проверка роли;
есть ли проверка пользователя;
не возвращает ли middleware 404 вместо 403;
какой конкретно участок backend формирует 404.
Шаг 4. Проверить разные серверы

Убедиться, что администратор и сотрудники обращаются к одному и тому же backend, одной версии приложения и одной БД.

Вывести:

frontend build:
backend version/commit:
API base URL:
database:
Шаг 5. Проверить curl/API напрямую

Выполнить один и тот же запрос:

с учётными данными администратора;
с учётными данными сотрудника.

Если admin получает 200, а employee получает 404 — показать точное место backend-кода, которое даёт различие.

Если оба получают 404 напрямую — проблема не в правах, а в route/UID/backend.

Критерий

Не писать «исправлено», пока не получены реальные результаты:

ADMIN:
/status → XXX
/tons   → XXX

EMPLOYEE:
/status → XXX
/tons   → XXX

И после этого выполнить операции через обычный интерфейс.

А вот что я подозреваю сильнее всего

Судя по двум 404 на одном скрине, я бы сейчас не обвиняла права сотрудников.

У сотрудников оба запроса:

/status
/tons

летят в 404.

Это может быть общий слой:

employee → frontend → API → какой-то middleware → 404

А не две независимо сломанные кнопки.

И ещё: на скрине видно, что UID уже URL-encoded (%D0%94...). Значит, предыдущий фикс encodeURIComponent() действительно попал в frontend. Поэтому теперь надо выяснить, почему уже правильно закодированный URL сервер всё равно возвращает 404.

А с «Разбить» у тебя отдельно остаётся backend-проблема /tons.
